# Rule File Standard

Этот reference задает canonical standard для файлов в `.cursor/skills/bitrix-core-best-practice/rules/`.

Цель rule-file: дать агенту короткие, проверяемые и применимые инструкции для выбора правильного Bitrix-паттерна в коде или на ревью.

## Основной принцип

Rule-file пишет инструкции для AI, а не общий обучающий текст для человека.

Это значит:

- правило должно помогать принять решение;
- правило должно быть сформулировано так, чтобы по нему можно было писать код или делать review;
- правило не должно расползаться в обзор всего фреймворка;
- правило не должно дублировать соседний rule-file без необходимости.

## Обязательная структура

Каждый новый или переписываемый rule-file по умолчанию должен иметь такой каркас:

```md
# <Rule Name>

## Boundaries
- что именно покрывает этот файл
- что входит в его зону ответственности
- что в него не входит

## Rules
- операционные нормы по применению сущности

## Example 1
...

## Example 2
...

## Example ...
...

## Checklist
- бинарные проверки `да/нет`
```

Этот блок задает только canonical skeleton.
За образцами заполнения секций смотри:

- [rule-file-example-minimal.md](rule-file-example-minimal.md) — default-ориентир для большинства новых rule-файлов;
- [rule-file-example-complex.md](rule-file-example-complex.md) — только для тем, где минимальной формы уже недостаточно.

Если файл простой, этого каркаса достаточно.

Если сущность сложная, разрешено добавлять:

- `## Decision Guide` — если нужно помочь выбрать между 2-3 подходами;
- `## Common Mistakes` — если есть повторяющиеся anti-patterns;
- `## Legacy / Exceptions` — если уместны осознанные отступления;
- `## Related Rules` — если границы с соседними файлами важны для понимания.

## Как писать Boundaries

`Boundaries` нужен, чтобы агент, уже открывший этот rule-file, не расширял его ответственность шире нужного и не смешивал соседние темы.

В `Boundaries` обязательно зафиксируй:

- какие сущности, API, классы, пути или сценарии покрывает этот rule-file;
- где граница ответственности файла;
- какие ближайшие смежные темы сюда не входят, если их действительно легко спутать с текущим rule-file.

Не перечисляй удаленные архитектурные слои и абстракции «для полноты». Если тема не конкурирует напрямую с controller, routing, DTO или другой областью, не тащи их в `Boundaries` автоматически.

Хорошо:

- «Этот файл покрывает `RoutingConfigurator`, `PublicPageController`, route params и правила объявления маршрутов в `<module>/install/routes/`».
- «Этот файл не описывает filters и `*Action()`; для них переходи в `rules/controller.md`».
- «Этот файл не описывает выбор ORM date/datetime-полей и не задает предметные правила календарных расчетов».

Плохо:

- «Этот файл про роутинг».
- «Используй при необходимости».

## Как писать Rules

Каждый bullet в `## Rules` должен выражать одну норму.

Предпочитай формулировки с явным действием:

- `Используй ...`
- `Не размещай ...`
- `Возвращай ...`
- `Группируй ...`
- `Ограничивай ...`

Избегай bullets, где в одной строке склеены:

- несколько независимых правил;
- правило и длинный экскурс;
- сразу 3-4 исключения;
- общая теория без операционного вывода.

Хорошо:

- `Для нового API веди маршрут на [Controller::class, 'action'] с явным HTTP-методом.`
- `Не используй any() для state-changing endpoint, если достаточно post() или patch().`

Плохо:

- `Используй контроллеры, помни про HTTP-методы, не забывай о безопасности, а если legacy, то там все зависит от страницы.`

## Типы норм

Не все правила одинаковы по силе. В тексте не обязательно писать формальные теги `MUST` / `SHOULD`, но различие должно быть ясно из формулировки.

Используй три типа норм:

1. Жесткое правило
   - Нарушение почти всегда означает ошибку или плохой паттерн.
   - Формулировки: `не используй`, `объявляй`, `держи`, `возвращай`, `только`.

2. Предпочтительный default
   - Это рекомендуемый путь по умолчанию, но возможны осознанные исключения.
   - Формулировки: `предпочитай`, `обычно`, `как правило`.

3. Допустимое исключение
   - Это не новый default, а явно ограниченный fallback.
   - Формулировки: `допустимо только если`, `используй только когда`, `исключение`.

Если правило допускает исключение, не прячь его глубоко в конце длинного абзаца. Лучше явно отделить основную норму от исключения.

## Негативные ограничения

По умолчанию описывай правильный путь, а не каталог плохих решений.

Если нужно предотвратить типичную ошибку, встраивай короткое негативное ограничение прямо в соответствующее правило:

- что не делать;
- почему это здесь неверно;
- какой путь считать правильным вместо этого.

Не выноси отдельный список anti-patterns без необходимости:

- он раздувает контекст;
- усиливает шум;
- может подсказать модели нежелательные варианты.

Отдельный блок с краткими anti-pattern bullets допустим только если без него агент стабильно выбирает опасный или дорогостоящий неверный путь.

Ограничения для такого блока:

- только короткие bullet-упоминания;
- без примеров кода;
- без длинных объяснений;
- не более 1-3 пунктов;
- только для действительно критичных ошибок.

## Related Rules и границы

Если тема пересекается с другим rule-file, укажи это прямо в тексте или в отдельной секции `## Related Rules`.

Новый rule-file не должен:

- переписывать соседний файл своими словами;
- спорить с ним молча;
- тащить в себя правила другого слоя «на всякий случай».

Вместо этого:

- коротко фиксируй границу;
- отправляй к соседнему файлу по имени;
- оставляй в текущем файле только то, что нужно для локального решения.

## Требования к примерам

Каждый пример должен быть self-contained настолько, насколько это возможно без лишнего шума.

Форму секции `## Example N` смотри в:

- [rule-file-example-minimal.md](rule-file-example-minimal.md) — базовый контракт примера;
- [rule-file-example-complex.md](rule-file-example-complex.md) — расширенный контракт для сложного случая.

Это значит:

- указывай нужные `use`-импорты;
- показывай только код, который реально иллюстрирует норму;
- перед кодом дай 1-3 предложения: что демонстрирует пример и почему это good pattern;
- не показывай огромные куски фреймворка без необходимости;
- не делай все примеры вариациями одной и той же мысли.

Минимальный набор примеров:

- один пример базового рекомендуемого паттерна;
- один пример важного исключения, edge case или соседнего сценария.

Для большинства простых тем этого достаточно.

Если тема сложная, добавляй столько `## Example N`, сколько нужно, чтобы покрыть разные decision points, compatibility paths, edge cases и исключения.

Не останавливайся на двух примерах, если в правиле остались самостоятельные важные кейсы без иллюстрации.
Не добавляй примеры ради количества, но и не делай число примеров фиксированным.

## Требования к чеклисту

`## Checklist` — это не пересказ файла, а быстрая бинарная самопроверка.

Каждый пункт чеклиста должен:

- проверяться по коду или diff без гадания;
- быть сформулирован как вопрос с ответом `да/нет`;
- помогать поймать типичную ошибку.

Хорошо:

- `Маршрут ведет на [Controller::class, 'action'], а не на legacy-страницу, если это новый API?`
- `В action осталась только orchestration-логика?`

Плохо:

- `Все ли хорошо с кодом?`
- `Правильно ли используется сущность?`

## Что делает rule-file сильным для AI

Сильный rule-file:

- быстро дает понять, когда он применим;
- помогает выбрать между несколькими похожими вариантами;
- явно показывает anti-patterns;
- содержит примеры, которые можно перенести в код почти без догадок;
- заканчивается чеклистом, по которому агент может быстро сделать self-review.

Слабый rule-file:

- состоит из общих фраз;
- не отделяет default от исключения;
- не показывает границы ответственности;
- дублирует документацию Bitrix без project-specific вывода;
- содержит примеры ради объема, а не ради решения.

## Рекомендуемый authoring workflow

При создании нового rule-file:

1. Определи точную сущность и границы файла.
2. Найди соседние rule-файлы, чтобы не пересечься с ними по ответственности.
3. Собери 5-12 сильных операционных правил вместо длинного неструктурированного списка.
4. Добавь anti-patterns и исключения там, где агент чаще всего ошибется.
5. Подбери 2-4 примера, покрывающих основной path и важные edge cases.
6. Сожми чеклист до быстрых бинарных проверок.
7. Перечитай файл глазами агента: можно ли по нему принять решение в реальной задаче без дополнительной теории.

## Критерии готовности

Rule-file готов, если:

- по `Boundaries` ясно, что именно покрывает файл и где проходят его границы;
- в `Rules` нет размытых и декоративных bullets;
- исключения не поданы как новый default;
- примеры реально поддерживают правила, а не повторяют их в другой форме;
- чеклист позволяет быстро проверить diff;
- файл не подменяет собой соседние `rules/*.md`.
